## 0. The short version

**There is no webshop.** Not a broken one — none. `src/lib/shopCatalog.ts` is a
complete, careful shop data layer and it has **zero callers**:

```
$ grep -rln "getShopProducts\|getShopProductBySlug" src/
src/lib/shopCatalog.ts        ← itself, and nothing else
```

There is no `/winkel`, no product page, no basket, no checkout. `0009_webshop_orders.sql`
exists in the database; nothing writes to it. Mollie is wired up, but only for a
technician taking payment at the kerb — the payment webhook says so in a comment:
*"The webshop's payments carry no `kind`"*. So what exists today is a very
thorough **service** site (lead capture, dispatch, CRM, voice agent, 3,627-article
internal catalogue) with a shop-shaped hole in the middle.

That is actually good news: nothing has to be unpicked. But it changes what
"change the look" means. The look is not the problem.

**The real problem is the one feature you named first.** "Customer enters his car
model and finds the suitable key" cannot be built honestly on today's data. Only
**20% of the public catalogue says which model it fits**, and only **10%** carries
year ranges. Measured against real cars:

| Customer types | Products returned | What they are |
|---|---|---|
| Mercedes C-Klasse 2016 | **0** | — |
| Toyota Yaris 2015 | **1** | a housing |
| Kia Ceed 2014 | 2 | a housing, a remote |
| Audi A3 2009 | 3 | 2 housings, 1 accessory |
| VW Golf 2012 | 9 | 3 blades, 5 housings, 1 remote — **no key** |

A model-and-year finder built on this returns an empty shelf for most of the
Dutch car park, and never returns the thing the customer came for. Section 2 sets
out what to build instead, which works today.

**Security**: the application code is better than most commercial shops I read —
RLS on all 46 tables, 98 policies, constant-time secret compares, webhooks that
verify and fail closed. The serious findings are not in the application logic.
They are a **live personal-data exposure in git history**, a **critical Next.js
advisory affecting the exact mechanism that gates your CRM**, and an
**image-processing library with known CVEs sitting behind an unauthenticated
upload endpoint**. Section 1, in order.

## 1. Security

Ranked by what I would fix first. Nine of these are twenty-minute fixes.

### 1.1 — CRITICAL: 24 customer phone numbers are still readable in git history

`google_ads_conversions.csv` was committed, then removed in `58133af` ("Remove
conversions export with customer PII from the repo"). **`git rm` does not remove
anything from history.** The file is still served in full by:

```
git show 6533e9f:google_ads_conversions.csv
```

Measured contents: 63 rows, 24 with a phone number filled, **0 hashed** — 23 are
plain Dutch mobile numbers in `06…` / `+316…` form, one malformed. `HANDOFF.md`
records that this repository **was public**. That makes this a personal-data
breach under GDPR Art. 33, not a tidy-up: the clock on the 72-hour assessment
started when you became aware, and awareness is now.

Do, in this order:

1. **Assume disclosed.** The repo was public; GitHub serves blobs from deleted
   refs and forks keep them. Treat the 24 numbers as leaked.
2. **Purge the history** — `git filter-repo --invert-paths --path google_ads_conversions.csv`,
   force-push, then **open a GitHub support ticket** to expire the cached blobs and
   check for forks. Rewriting alone does not unpublish them.
3. **Write the Art. 33 assessment down**, even if you conclude no notification is
   needed. Phone numbers alone, 24 data subjects, no financial or special-category
   data — a defensible "no notification" outcome, but only if the reasoning is
   recorded before someone asks.
4. The `.gitignore` entry now blocking `*conversions*.csv` is correct and should stay.

Related, and already in `HANDOFF.md` §7, still open: **rotate the Supabase
`service_role` key** (pasted into a chat) and **change the CRM password** for
`info@autosleutel24.nl` (its literal value was written in a doc in this public
repo). The service-role key bypasses every RLS policy in section 1.4 — it is the
single most valuable credential you hold. Rotate it before anything else ships.

### 1.2 — CRITICAL: `next@16.2.4` carries a Middleware/Proxy bypass advisory

```
$ npm audit
17 vulnerabilities (1 critical, 14 high)
CRITICAL  next  — Denial of Service with Server Components;
                  Middleware / Proxy bypass in App Router
```

`src/proxy.ts` is what gates `/admin` and `/api/admin/*`. A proxy-bypass class
advisory lands directly on your access control.

What saves you is a decision already made in this codebase: `proxy.ts` does an
*optimistic* cookie check and the real authorisation lives in
`src/lib/crmSession.ts`, next to the data, with `getUser()` revalidating the token
against the Auth server. A bypass therefore reaches pages that then turn the
caller away themselves. That is defence in depth working exactly as intended —
credit where it is due.

Fix is a patch upgrade, not a migration: **`next@16.2.4` → `16.4.0`**
(`isSemVerMajor: false`).

**Applied in this branch.** Typecheck and build both pass on 16.4.0, and
`npm audit` now reports **0 critical** (was 1) and **10 high** (was 14). The
`postcss` high cleared with it.

### 1.3 — HIGH: `sharp`/libvips CVEs are reachable from an unauthenticated endpoint

`src/app/api/upload/route.ts` takes an image from anyone on the internet — no
session, rate-limited to 10/hour/IP — and for HEIC runs it through
`heic-convert` (WASM libheif) and then `sharp@0.35.3`. Audit:

```
HIGH  sharp — inherited vulnerabilities in libvips: CVE-2026-33327,
              CVE-2026-33328, CVE-2026-35590, CVE-2026-35591
```

Attacker-controlled bytes into a native image decoder with known CVEs is the
textbook reachable path.

**And a packaging bug in the same file:** `sharp` was declared in
`devDependencies`, but this is a production route. It worked on Vercel only
because the build installs dev dependencies. Any `npm ci --omit=dev` deploy would
have given a 500 on every HEIC upload.

**Both applied in this branch:** `sharp` 0.35.3 → 0.35.5, moved to
`dependencies`. The server-side re-encode in §1.6 is still to do — that is the
change that actually hardens this route, rather than just patching the decoder
under it.

### 1.4 — HIGH: a technician can rewrite their own job's price and commission

This is the finding with money attached, and it is the one I would fix before
onboarding a single independent technician.

`jobs` carries `quoted_price`, `final_price` and `commission_amount`. The grant
is table-wide:

```sql
grant select, insert, update on public.jobs to authenticated;
```

and the row policy lets a `monteur` update their own jobs:

```sql
create policy jobs_monteur_update on public.jobs
  for update to authenticated
  using ( public.crm_role() = 'monteur' and technician_id in (…) and scheduled_date between … )
```

Nothing restricts *which columns*. A technician holding a `monteur` JWT can call
PostgREST directly — not through your CRM, which never offers these fields — and
set `final_price` or `commission_amount` to whatever they like on their own
completed job. Your whole platform model is 8–25% commission computed from those
numbers, and the people holding those JWTs are contractors with a direct
financial interest in them being lower. `updated_by` is self-settable too, so the
audit trail agrees with them.

You already use the right pattern elsewhere — `0017_payout_permissions.sql`:

```sql
grant update (status, paid_at, notes) on public.payout_requests to authenticated;
```

Here a column-level grant alone won't do, because the office writes `jobs`
through the same `authenticated` role (not the service-role client). So:

- **Preferred:** a `before update` trigger that raises when `crm_role() = 'monteur'`
  and any of `quoted_price`, `final_price`, `commission_amount`, `technician_id`
  or `updated_by` changed. One function, no route changes, office path untouched.
- **Or:** move the technician's own-job writes behind a `security definer` RPC, as
  `crm_respond_to_offer()` already does, and drop `jobs_monteur_update`.

Lower severity, same policy: `jobs_monteur_update`'s `with check` omits the
`scheduled_date between` clause that its `using` has. A technician can therefore
push one of their own jobs out of the window — which also removes it from their
own list. A quiet way to drop an assigned job. Mirror the clause into `with check`.

### 1.5 — MEDIUM: the upload endpoint trusts the declared Content-Type

The allowlist in `/api/upload` reads `request.headers.get('content-type')`. The
bytes are never inspected. Send `Content-Type: image/png` with any payload and it
is stored public and re-served from `autosleutel24.nl/f/leads/…`.

XSS is blocked — the stored `contentType` is forced to an image type and
`X-Content-Type-Options: nosniff` is set, so a browser will not execute it. The
residual risk is **your domain hosting arbitrary files**: malware or a phishing
payload on a first-party URL, fetchable with `curl`, and your domain reputation
carrying it. Rate limiting and `addRandomSuffix` keep it small, not zero.

### 1.6 — MEDIUM: customer GPS coordinates get published with lead photos

Every upload path calls `toWebp(file).catch(() => rawFile)` — a best-effort
*client-side* canvas re-encode. Canvas strips EXIF when it works. When
`createImageBitmap` cannot decode that particular file, **the original camera
JPEG is uploaded unchanged**, and the server only strips metadata on the HEIC
branch. A customer photographing their car outside their house sends you a JPEG
with GPS EXIF, and it is served from a public URL.

**One fix closes 1.5 and 1.6 together.** Run *every* accepted upload through
`sharp(buffer).rotate().webp({quality: 82})` server-side, as the HEIC branch
already does. Decoding validates the magic bytes (so the declared type stops
mattering), re-encoding drops all metadata, and the output is the WebP you wanted
anyway. Reject anything sharp cannot decode.

### 1.7 — MEDIUM: no Content-Security-Policy, and you are about to take cards

`next.config.ts` sets `X-Frame-Options: DENY`, `nosniff`, HSTS with
`includeSubDomains`, a sensible `Referrer-Policy` and a tight
`Permissions-Policy`. Good. There is **no CSP** — confirmed, nothing in
`next.config.ts` or `src/`.

Acceptable for a brochure site. Not acceptable the moment a checkout exists:
you load Google Ads, Clarity and Vercel Analytics, and any one of those tags
turning hostile can read a payment form with nothing to stop it. **PCI-DSS 4.0
requirements 6.4.3 and 11.6.1** — mandatory since 31 March 2025 — specifically
require script management and change detection on payment pages. Even with Mollie
hosting the card entry (SAQ A), you need these for the page that redirects.

Add a CSP before checkout ships, report-only first. Next's nonce support makes
this straightforward; the one real cost is enumerating your tag domains.

### 1.8 — MEDIUM: `xlsx@0.18.5` parses uploaded invoices and has no npm fix

```
HIGH  xlsx — Prototype Pollution in sheetJS; ReDoS     fixAvailable: false
```

`/api/admin/invoice` does `await import('xlsx')` on a file a user uploaded.
Authenticated-only, so the blast radius is your own staff and technicians — but
that is precisely the population in 1.4.

`fixAvailable: false` is not "unfixable": SheetJS left npm. The patched release
lives on their own CDN (`https://cdn.sheetjs.com/xlsx-0.20.x/xlsx-0.20.x.tgz`),
installed as a URL dependency. Alternatively `exceljs`, which is still on npm.
Either way, 0.18.5 should not stay. **Still outstanding** — it needs a real
decision about which library, so I left it rather than swapping it silently.

### 1.9 — MEDIUM: rate limiting fails open, and nothing checks that it is on

`src/lib/rateLimit.ts` returns `{ ok: true, degraded: true }` when the Upstash
variables are missing. Documented and deliberate — a missing env var must not
take the site down. The gap is that **nothing surfaces the degraded state**. If
`KV_REST_API_URL` is unset in production, every limit in the app is silently off:
lead spam, RDW lookups, and the blob uploads in 1.3 and 1.5.

`rateLimitConfigured` is already exported. Log a warning on boot when it is false
in production, or assert it in a health endpoint. The limiter does not need to
change — you just need to know.

### 1.10 — LOW

- **Cron secret compared with `!==`** (`/api/cron/sync-marketing`). Every other
  secret in this codebase uses a constant-time compare; use `safeEqual` here too
  for consistency, though timing a secret over HTTP is not practical.
- **1.1 MB of scraped HTML committed** — `google_search.html`, `akey_product.html`,
  `akey_obdstar.html`, plus `build_errors.log`, `ts_errors.log`, `output.txt`,
  `prompts.txt` (61 KB) and a dozen one-off `fix_*.js` scripts in the repo root.
  No security impact; it makes every secret scan unusable (my first scan returned
  1.1 MB of base64 from these files and nothing else). Delete them, and watch the
  ~500 MB of product images `HANDOFF.md` already flags.

### What is genuinely well built

Worth stating plainly, because it should not be touched during the redesign:

- **RLS is complete.** All 46 tables created in `supabase/migrations/` have
  `enable row level security`, with 98 policies and zero tables left policy-less.
  (My first pass reported 14 tables unprotected; that was my own grep failing on
  the aligned whitespace in the migrations. The posture is sound.)
- **The role comes from the JWT** (`app_metadata.role`), which a user cannot write,
  not from a table a user can.
- **`leads` is office-only** with no insert policy at all — leads are written with
  the service-role key from `/api/leads`. A technician cannot read the lead table
  even by calling PostgREST directly. That is the right call and it is enforced
  where it counts.
- **The Mollie webhook is correct**: it accepts only an id, re-fetches the payment
  with your own key, scopes on `metadata.kind`, and is idempotent for retries. A
  forged POST cannot mark anything paid.
- **Telegram and ElevenLabs webhooks verify** (secret header, HMAC) and fail closed
  when the secret is unset.
- **`getClientIp` reads `x-vercel-forwarded-for` and takes the *last* XFF hop** —
  the comment records that reading `[0]` once let an attacker mint a fresh rate-limit
  bucket per request. That is a real bug, found and fixed properly.
- **Constant-time compares** in `adminAuth.ts` and `agentAuth.ts`; `agentAuth` also
  refuses a secret shorter than 24 chars.
- **The agent never composes a price** and `/book` recomputes server-side. Exactly
  right: a caller who talks the agent into a number cannot make it binding.

## 2. Products — can we actually sell this?

Rebuild the catalogue yourself with `npm run catalog`; `node scripts/audit-catalog.mjs`
checks the invariants.

```
3,627 articles — public 2,108 · trade-gated 1,519
with a photo 3,626 · with a price 3,500 · spec table 3,619
61 makes · 850 models · 41 held back for review · 314 flagged for check
audit: no failures, 135 warnings (127 of them "no price")
```

The classification pipeline is the strongest part of this project. Category comes
from A-Key's own JSON-LD breadcrumb, never from words in a title; an unmapped
shelf **fails the build**; articles without evidence are held back rather than
filed wrong. That is why I trust the numbers below enough to plan on them.

### 2.1 The finder problem, precisely

Public catalogue, fitment coverage by category:

| Category | Public | Has make | Has model | Has years | Has price |
|---|---:|---:|---:|---:|---:|
| Sleutelbehuizingen | 440 | 438 | 156 | 121 | 316 |
| Sleutels zonder startonderbreker | 366 | 82 | 10 | 1 | 366 |
| Accessoires | 312 | 75 | 20 | 4 | 311 |
| Afstandsbedieningen | 262 | 261 | 108 | 54 | 262 |
| Universele sleutels | 172 | 62 | 14 | 0 | 172 |
| Transpondersleutels | 118 | 109 | 22 | 0 | 118 |
| Sleutelbaarden | 92 | 72 | 17 | 1 | 92 |
| Batterijen | 74 | 2 | 0 | 0 | 74 |
| Smart keys / keyless | 71 | 71 | 42 | 26 | 71 |
| Transponders | 46 | 9 | 4 | 0 | 46 |
| Noodsleutels | 38 | 32 | 5 | 0 | 37 |
| Printplaten (PCB) | 34 | 30 | 6 | 6 | 33 |
| **Total** | **2,108** | **1,272** | **416** | **214** | **1,981** |

**60% has a make. 20% has a model. 10% has a year range.** And 836 public
articles have no make *and* no fitment at all — mostly batteries, universal
remotes and uncut blanks, which genuinely fit many cars, so that is honest data,
not missing data.

A strict make→model→year filter therefore fails, and it fails worst where it
hurts most: on the finished key the customer actually wants. Of 995 public
"an actual key" articles, only 197 name a model, 301 name a chip, 338 name a
frequency.

### 2.2 What does work: make-first, model as refinement

At **make** level the same catalogue is healthy — 40 to 120 products for every
major Dutch make:

```
Hyundai 118 · Opel 117 · Renault 112 · Toyota 111 · Ford 93 · BMW 84
Citroën 82 · Volkswagen 81 · Kia 77 · Peugeot 75 · Mercedes-Benz 71
Fiat 66 · Nissan 52 · Audi 43 · Dacia 37 · Suzuki 34 · Seat 33 · Volvo 22
```

So build the finder as **make → model → year, where each step narrows but never
empties**:

1. **Make** — a real filter. Always returns a full shelf.
2. **Model** — promotes exact-fitment matches to the top under
   *"Past op uw Golf"*, and keeps the rest of the make below under
   *"Past op andere Volkswagen-modellen — vraag ons na"*. Never hide the
   remainder: for 80% of the catalogue, "no model stated" means A-Key stated
   none, not that it doesn't fit.
3. **Year** — refinement only, and only against the 214 articles that carry
   ranges. An article with no years is never excluded by a year.

`src/lib/catalog.ts` already has the machinery for this — `buildFacets()`
deliberately counts each facet against the result set *excluding its own
selection*, which is the thing most shops get wrong. The missing piece is
ranking, not filtering.

Two more things the customer can answer that the data supports better than model
does: **frequency** (338 keys) and **chip/transponder** (301) — both readable off
the old key, both already facets. For a visitor who has their old key in hand,
that is a more reliable path to the right part than the model dropdown.

And keep the **RDW plate lookup** (`/api/kenteken`) as the fast path — it returns
make, model and year from the plate, so the customer fills the finder by typing
six characters instead of three dropdowns.

### 2.3 What this catalogue actually is

Look at the shape again: 440 housings, 366 uncut blanks, 312 accessories, 92
blades, 74 batteries, 34 PCBs — against 71 smart keys and 118 transponder keys.

**This is a repair-parts catalogue, not a finished-keys catalogue.** That is not a
flaw; it is a positioning fact, and it happens to fit the business you already
have:

- **Shop** sells what a customer can fit themselves, or have fitted: a housing for
  a key whose buttons have worn through, a blade, a battery, a PCB. High margin
  on cheap parts (your tier table already does this — 3.0× under €5, 1.35× over
  €150), low support burden, no programming risk.
- **Service** sells the rest. A smart key needs programming at the car; that is
  the dispatch business, already built, with `quote.ts` refusing to price when a
  make's keys span more than 1.8× rather than guessing.

The shop should say this out loud on every key product page: *"Deze sleutel moet
bij de auto geprogrammeerd worden — bestel met montage, of laat ons komen."*
That converts the catalogue's weakness into the service funnel instead of into a
return.

## 3. Problems — what actually blocks a sellable shop

In dependency order. Each is a thing that does not exist, not a thing that is broken.

1. **No public shop surface.** No `/winkel` listing, no `/winkel/[slug]` product
   page. `getShopProducts()` and `buildFacets()` are ready and uncalled.
2. **No basket, no checkout, no order.** `0009_webshop_orders.sql` exists and
   nothing writes to it. The shop's Mollie webhook is referenced in a comment and
   does not exist. Note `src/lib/catalog.ts` already has `shippingFor()`.
3. **No VAT or invoice on a product order.** `VAT_RATE` is applied inside
   `shelfPrice()`, so prices are gross — but there is no order line that records
   the VAT split, which a Dutch BTW return needs. The service side already has
   `sales_invoices` and `invoiceLines.ts`; product orders need to reach the same
   ledger or your bookkeeping has two halves that do not add up.
4. **No returns path.** You sell to Dutch consumers: 14 days' withdrawal is
   statutory, and the terms must say so *before* the order button. An electronic
   key that has been programmed to a car is arguably exempt as customised goods —
   which is exactly why the shop/service split in §2.3 needs to be explicit on the
   product page, not buried in `/algemene-voorwaarden`.
5. **Fitment is advice, and has to read like it.** With 80% of the catalogue
   carrying no model, "past op uw auto" would be a claim you cannot stand behind.
   "Volgens onze leverancier past dit op …" with the supplier's own `vehiclesRaw`
   shown is both true and more useful. `HANDOFF.md`'s rule — *never invent* —
   applies to fitment as much as to price.
6. **Then the look.** It is last for a reason: the design tokens in
   `src/app/globals.css` (navy/orange scales, semantic aliases) and the CRM's
   `theme.css` are a usable system. The site does not need a new palette; it needs
   the three pages that do not exist yet — finder, listing, product — designed
   well, and the existing hero/trust blocks tightened around them.
7. **Nobody has walked the app signed in.** Per `HANDOFF.md` §7, the CRM redesign
   was verified by rendering stylesheets, not by using it, because there is no
   login. Still true, and it blocks the technician onboarding wizard that §6 calls
   the actual blocker.
